## 2. 测量有效性前提（三类"仪器本身在骗你"）

1. **沙箱策略影响结果**：`workspace-write` 沙箱下 **`/dev/shm` 不可写** ⇒ SE-Bench Phase1 得出
   **12/17 而非 17/17 的假 FAIL**。验收**只能在 `danger-full-access` 下跑**。
   （`docs/MI250X-mi210-vllm-本机应用方案-2026-09-08.md` §2.4/§6 L125-129）
2. **指令预算 65536 会静默降级**：超预算时 **`AGENTS.md` 整份不进上下文**、`CLAUDE.md` 从尾部截断。
   加指令内容前必跑 `tools/instruction_budget_check.sh`。
   （`docs/DSH-指令预算挤掉AGENTS-根因与修法-2026-09-12.md`；`tools/instruction_budget_check.sh:5-12`）
3. **profiler 有计时地板**：`rocprofv3` 在本机 `copyBuffer / quantize_q8_1 / k_bin_bcast / scale_f32 / unary_op`
   的中位数**全是 4.96 µs** ⇒ **不是真实时长**，合计被系统性抬高。
   **判据：只信中位远离 4.96 µs 的桶。** 这条会污染**任何** profile 归因。
   （GLM-5.3 全记录 §6.10 L767-770）

## 3. 判据设计（最容易造出"假绿"的地方）

- **判据必须有区分度：无负对照的"全绿"等于没测。**
  正面例子：compressor 池化对拍最佳变体 corr=0.999999、**错误变体 corr=0.086** ⇒ 才有证明力。
  （`docs/DeepSeek-V4.1-Flash-CT-INT4-W4A16-转换记录-2026-09-18.md` §4.30 L1893-1910）
- **判据必须对置换敏感。** 用"每位置 `max|v|` 对比 `448*scale`"判布局是**错的**——
  对 d 取 max 是**置换不变**的，两种读法给出完全相同的比值（都是 796.44）⇒ 零区分度。
  真正一刀切开的是"**写入 → 读回对比原值**"。
- **`grep 关键词` 不能判"机制不存在"。** 「关键词不存在 ≠ 机制不存在」：
  `grep -c encoder == 0` 曾让我误判 V4.1 不是 CED，而**权重旁边就有 README**。
  二次确认法 = **权重存在性 == 模式表**。转换记录 §4.24 L1274-1320
- **注释不是证据；存储 dtype ≠ 表示精度。** 压缩 KV 的落盘方式**只能从内核看**
  （`_rope_quant_insert_kernel` 只有 bf16 与 fp8-e4m3，`store_fp8` 是编译期分支、**没有 fp4 分支**）；
  bf16 cache 里可以放 fake-quant 值。转换记录 §4.21 L1078-1130
- **探针要加"真实请求门"**：vLLM 用**合成 warmup/profile dummy 批**（实测
  `input_ids=[201,0,1,2,…]`、`positions=[2,0,1,2,…]`）⇒ dump 探针必须断言 `positions == 0..T-1`。
  另：`tensor.float().cpu().clone()` 在非默认流上与 caching allocator 复用竞争，
  污染落在大张量**尾部** ⇒ 大张量要么 GPU 端只打印统计，要么 `clone()`→`synchronize()`→`cpu()`。
  转换记录 §4.10 L435-467
- **cos 类统计不能用手写 float32 点积**：1180 万项相消会把 0.9948 报成 0.9628。
  一律 `F.cosine_similarity` 或 float64，并做 `relRMSE 10% + cos 0.995` 自洽检查。转换记录 §4.15 L626-665
- **验证实例是否编进去要按模板参数位置解析**，**不能 `grep 256`**：宏里 `PSIZE=256` 也命中，
  会得到"旧 `.so` 匹配得更多"这种荒谬结果——**那正是指标错的信号**。
  （`docs/MI250X-attention-hd256-内核缺口-2026-09-07.md` §7 L114-138）
- **`is_supported()` 报 True 不代表能跑**：NVFP4 的 FP8 侧先打
  `Selected ChannelWiseTorchFP8ScaledMMLinearKernel`，运行时才崩
  `torch._scaled_mm is only supported on … MI300+` ⇒ **必须真跑一次**（ dummy 构建探测）。
  （`docs/MI250X-safetensors模型硬件加速适配清单-2026-09-04.md` §4.1 L110-120）
- **自己写的转换，永远不能用自己写的读取器验收**（闭环自证：两边同错 ⇒ 全绿）。
  必须用厂商代码 / 运行时自己的解包实现当第三方尺子。
- **pgrep 的括号技巧只在"裸串全篇不出现"时安全**：`pgrep -f "[s]erve_and_eval"` 报 1 是**自匹配**
  （同一命令行后半段的 `grep … serve_and_eval.sh` 含裸文件名）。判进程要看 `ps` 明细
  （`etimes=0` 认出是自己）。转换记录 §4.23 L1218-1271
- **护栏必须自己验证自己**：一个恒真的"等待"比没有等待更危险
  —— 按 **MiB** 解析 `mem_info_vram_used`（实际单位是 **bytes**）恒得 0。GLM 全记录 §9.3 L1115-1117
- **换代是否真生效的判据 = 映射的库文件**（`${ROCM_PREFIX}/lib/libamdhip64.so.7.*` 必须含 `"7.15"`），
  **不是 `torch.version.hip`**。`docs/ROCm-10.0.0-vLLM-Flash-Next-TP8-本机实测-2026-09-12.md` §2 L41-53
- **"等显存释放"不能只轮询 sysfs，要同时看 PID 是否真退**（ROCm 10 的 Worker 无视 SIGTERM，
  否则等待循环会到点就走、被自己的护栏**正确**拒起）。同文 §7 L151-163
- **静默期不是卡死**：专家 repack（47,232 张量）**10–20 分钟零日志**、CPU 满转、零缺页、零磁盘读。
  判死前先看 CPU 增量与缺页增量。误判"卡死"而杀掉正常臂是极大的时间浪费。
- **`tokens/step` 是文风函数**：`ignore_eos=True` + 短 prompt 会逼出退化重复 ⇒
  `tokens/step` 崩到 2.06/2.59/1.93 而 **`ms/step` 三档纹丝不动（43.2~43.8）**。
  「**ms/step 不动**」本身就是"步没问题、是 tokens/step 在崩"的信号。
  ⇒ **测投机必须同时报 ms/step 与 tokens/step，且用自然散文。**
  （`docs/MI250X-PR41-Qwen38-27B-INT8-dflash-本机复现-2026-09-14.md` §5.1 L99-122）

## 4. 跨模型 / 跨量化不可外推的判例集

本节是"适用范围分层"的**存在理由**——每一条都是"看起来一样、根因不同"或"结论相反、适用域不同"。

- **int8 的两条相反结论都对，只是适用域不同**：「int8≈bf16、别走 int8」对
  **MoE / batch-1 / 内存受限**成立；wu1w 的场景是 **dense 线性 + Triton-INT8 基线太差**，
  CK 核修的是 **Triton 低效而非 MFMA 速率**。
  （`docs/davetha-wu1w-gfx90a-落地施工单-2026-09-10.md` §C L55-57）
- ⚠️ **未决矛盾**：**INT8-Attn 的步时比 int4 短 20%**（count 89.29→107.84 t/s；`step ms` 48.4→38.7），
  而技能第四轮记的是「把注意力/GDN 也拉进 INT8 **不加分**（−8.5%）」。
  两者**模型/镜像/口径不同** ⇒ **并列写清，不得择一引用**。
  沉淀出处 `docs/Ornith-397B-INT8Attn-提速-经验迁移-2026-09-18.md` §0.2 L53-66。
  同文还给出「**别搬**」清单：① 自研 GEMV 式 MoE 内核在**真实调用形状**（M=24/240 pairs）下
  **更慢**（261.4 vs 194.1 µs，−26%），只在 ≲80 pairs 才赢；② int4 的 KV 池/并发数字不可搬
  （本臂权重 2 倍、KV 只有 387k）。
- **「任何『这个臂更快』的说法必须同时给 `step ms`，否则可能只是在比草稿命中率」**（同文 §0.1 L49）。
- **`Qwen3.8-27B` 全系是 dense GDN 混合体（E=0）** ⇒ MoE 调优表**不适用**；
  **fp8-KV 对 27B 无收益**（KV 大头在 GDN 态）。同文 §C L29
- **构建升级的收益只在长上下文显现**：b136→b223 decode +15~17%、20k prefill ×1.59。
  GLM 全记录 适用域行 L210

## 5. 闸口自身的已知缺陷（元层）

- 🔑 **闸口绿 ≠ 脚本干净**：某次评审 4 个 `audit_*.py` **全绿**，却与 **9 项配方漂移 + 2 项 P0 并存**
  ⇒ `pkill` / 凭据两类红线当时**没有任何闸口覆盖**（后补 `audit_kill_discipline.py`）。
  **教训：闸口覆盖面 ≠ 红线清单。**
  （`docs/脚本评审-2026-09-16.md` §4 L118-119）
- ⚠️ **`tools/audit_log_paths.py:86` 有漏检**：检测式
  `re.search(r'^(?:export )?(LOG|LOG_FILE|PID|PID_FILE|PIDF)=.*"/tmp', txt)`
  **只匹配"变量赋值且必须带引号"** ⇒ 漏掉 ① 命令重定向 `… >/tmp/x.log`
  （**8109 臂 4 处正因此漏检、闸口却报绿**）② 无引号赋值 `LOG=/tmp/x` ③ 其它变量名
  （`OUT`/`SK_LOG`/`TMPLOG`）。建议扩成"任何含 `/tmp/` 的写点都算违规"，白名单放 `mktemp`。同文 §4 L104-117
- **别把补丁队列的自检"构造性做真"**：新改动一律**追加**，不要重生成旧片——
  重生成会让"队列==树"恒真，自检从此失去判别力。
- **值得肯定、不要改坏的设计**（同文 §3 L91-94）：`bench/ledger.py` 判决台账 + `gate` 子命令
  （**重提已被判负的方向直接 `exit 1`**）＝机制化防重复踩坑；`kernel_sha.py` 把**"裁判侧"也做 sha 断言**；
  `mtp_ab_recompute.py`（重算而非复读）。
- **本仓技能侧闸口的两条自证**：`audit_skill_recipes.py` 的主题漂移检查是用「往
  `environments.json` 注入一条假的 `AITER_JIT_DIR` 声明」实测过的（检出后回退）；
  `scope_match.py --env-check` 首跑即抓出一处真的版本轴不一致（llama.cpp 一棵树含多个 commit 子前缀）。

## 8. 报数协议六条（TPS 最容易记错账的地方）

> 出处 `docs/recipes/knobs/vllm-prefix-reuse-measurement.md`（`bench/ledger.jsonl` L45–L48）。
> **本机关于『复用有没有生效』『TPS 涨没涨』的错结论全部出在口径上**——
> 三条独立成因：命中计数器不区分内容、冷 boot 的 Triton JIT 尖峰伪装成『配置变慢』、
> 并行会话的 CPU/内存争用伪装成『内核退化』。

1. 固定 prompt + **丢弃首个** + 中位数（**n≥5**）；离群点要单独解释来源，不许混进中位数了事。
2. 🔑 **必须同形状预热**。冷 boot 后前若干请求会撞
   `Triton kernel JIT compilation during inference`
   （`_qsa_sparse_paged_gqa_splitk_kernel` / `_rejection_kernel` / `_resample_kernel` /
   `_compute_local_logits_stats_kernel`），而**短请求（『Say OK.』）覆盖不到这些内核**。
   实测后果：出现 12.64 t/s（≈30 s/请求）的离群点，**spread 从 1.1% 拉到 87%**。
3. 🔑 **报数必须同时给 `acceptance` 与 `step ms`**。同一臂两条 workload 的 step 可以几乎相同
   （**38.9–40.2 ms**），而 29% 的 TPS 差**全部**来自 MTP 接受率（**89.9% vs 61.2%**）
   ⇒ 只报 t/s 会把"接受率变化"读成"内核变快"。
4. **核他会话负载，不只看显存**。本机常驻并行会话（实测 `convert_dsv41_ct_int4.py`：
   **1305% CPU、RSS 56.7 GB、free 1 G + swap 10 G**）会造出 12.64 t/s 这类停顿，
   **而显存看起来『没人占』**。
5. **跨 boot 不可比**（σ≈4.6%）；同一 boot 内的 A/B 才可信，**三 boot 配对是底线**。
6. 🔑 **正确性容差要建在引擎的先天抖动上**：同稳态请求 token 逐位相同，
   但 **`|Δlogprob|` 可达 0.11**（MoE/QSA 归约次序）⇒ **用 ≤0.01 判『复用改变了输出』必然误判**。

**前缀复用的判据只能用耗时**：本机 6.7k tok 实测
**新 prompt 2.51 s / 整段命中 0.45 s / 部分命中 1.59 s**。
⚠️ `vllm:prefix_cache_hits_total` 与引擎周期行 `Prefix cache hit rate: X%`
在本版**不区分内容**（全新 prompt 也报 ~90%）⇒ **不能当判据**。
探针两坑：标签要每次唯一且**写进每一行**；**salt 必须放最前**
（放末尾会让『冷』那一次其实命中旧 prompt 的块）。

⚠️ **未解决**：重复 prompt 的『命中』计数在本底座**恒 0**，而耗时显示复用确实发生
⇒ 计数口径与实现不一致，**以耗时为准**；多轮块对齐上限（期望 0/400/800/1200）从未达标过。

## 9. 一条完整的撤回案例（**方法论级**）

> 出处 `docs/recipes/patches/qwen4exp-mtp-prefix-reuse.md`；`bench/ledger.jsonl` L48 撤回 L44。

- **09-18 的结论**：补丁让 prefix-cache 命中从"恒 0"变 **+3200/3686 = 87%**、
  多轮 TTFT 1.43–1.86 → 0.28–0.71 s ⇒ 于是把它的默认打开并写进 launcher。
- **09-21 三 boot 配对复测推翻**：补丁只把启动日志里那 **9 行警告**变成 0 行，
  **复用行为一项没变**。最可能的误因就是 §8 第 2 条——
  **把"冷 boot 首个请求撞 Triton JIT"当成了『没补丁就慢』**。
- 🔑 **可复用的判据**：`every group — including Mamba groups — will be treated as a draft
  group … prefix-cache reuse across requests will be disabled`
  这 9 行警告说的是『组被当成草稿组』，**不等于『复用为 0』**。
  **上游默认本来就有跨请求复用**（同 prompt 连发，第 3 次起整段跳过预填充 2.51 → 0.45 s）。
- **沉淀纪律**：警告**消失** ≠ 行为**改变**。判"补丁生效"必须找一条与警告无关的独立尺子
  （这里是 prefill 耗时），并按 §8 的配对 protocol 复测。

该 launcher 内 7 道 fail-closed 门：①模型目录 ②`nc` 端口门 ③HF offline
④功率档**只读**校验（560 W）⑤草稿组标注准入（`--require`）⑥8 die 显存前置门
⑦同端口实例存活门（核 `/proc/<pid>/cmdline`，防 PID 回收误拒）。

🔑 **教训（这才是可复用的部分）**：本臂 QR 那条准入断言曾因写了**不存在的补丁路径**而退化成
「**QR 永远开不起来**」，且**长期无人发现**——因为默认 `QR=0` 恰好掩盖了它。
⇒ **每道门都要故意触发一次**，确认它在应该红的时候真的红。
这与 §5「闸口绿 ≠ 脚本干净」、以及 `scope_match --env-check` 首跑即抓错是同一件事：
**一扇门若从不变红，它与"没有门"在行为上不可区分。**

## 11. 不占 GPU 验证 launcher 接线（**桩干跑**）

`VLLM_PYTHON=<桩脚本>` + 私有端口 + `VRAM_FREE_MIN_GIB=0` 干跑，
核对 env 与落盘路径——**全程不碰 GPU**。
本会话靠它证明了 6 项接线生效。

⇒ 这是「**需要 GPU 的结论一律先提方案等批准**」这条红线的**正面配套**：
绝大多数"接线对不对 / env 有没有生效 / 路径落哪"的问题**根本不需要卡**，
用桩干跑就能答，别为它去占 8 张卡。（对照 `stack_probe.sh` 的 `SKIP_BOOT=1` 同理。）
